GUI Surface — the fourth tile

Design study for the gui surface — a remote-desktop lens in run-kit. Supersedes PR #71 and the 2026-07-14 desktop-view plan; builds on window-views.md / surface-layout.md. Written 2026-09-09 in a /fab-discuss session; decisions in §16 are recorded, the execution plan is fab/plans/sahil/26-09-09-gui-surface.md.

Recommendation in five lines
  1. It is a surface, not a window. A fourth kind in the existing registry (tty · code · web · gui) — the 4th toggle button, ⌘4, palette rows, zen, zoom, mobile switch group all come free from the layout manager. Content is the host's screen, so the tile is available on every tab, exactly like code.
  2. One GUI session per host, supervised in an rk-gui sibling tmux session on the rk-daemon socket (the rk-code-server pattern). Off by default; one explicit switch, gui.enabled, both runs the VNC and shows the 4th button (§14). Per-session desktops stay possible later; nothing in v1 forecloses them.
  3. Protocol: RFB (VNC) over rk's own WebSocket relay, rendered by the stock noVNC library inside the tile. One client covers Linux and macOS. Never expose VNC on TCP; Linux uses a unix socket by convention under $XDG_STATE_HOME/run-kit/gui/.
  4. Linux = a private virtual display (TigerVNC Xvnc + a window manager — already installed on this VM). macOS = mirror the one live session via Apple Screen Sharing (noVNC speaks Apple's ARD auth). A Mac has no cheap "second desktop"; say so up front.
  5. Smoothness is a measured upgrade lane, not a v1 bet. Tight/JPEG over WS is fine for browsers and IDEs. If it isn't, swap the Linux backend for KasmVNC (H.264/AV1 since 1.5, WebP, multithreaded) behind the same tile. WebRTC-class stacks (Selkies, neko) fail run-kit's single-origin/tunnel constraint unless run in WS mode, and only Selkies has one.

1. Where it sits in the model

The screenshot's three buttons are the surface-toggles group: open-tile toggles over the shared registry in lib/surface-layout.ts (SURFACE_GLYPH, SURFACE_LABEL, availableTiles), with ⌘1/2/3 in keybindings.ts. The fourth button is one more row in that registry:

Glyph is a placeholder; anything two-cell and ASCII-adjacent works ([], ▣, ⎚). The existing vocabulary is "what the tile shows" (prompt, braces, scheme), so a framed-screen glyph fits.

What comes for free: ⌘4 toggle, overflow-menu checkbox row, palette Toggle GUI / Tile: Switch to GUI, zen (⇧Enter hides top bar + sidebar and zooms the focused tile), tile zoom ⛶, promote/swap/close, mobile switch group radio, 3-tile cap, degradation ladder, @rk_win_layout sharing (rk tab layout --add gui works day one).

R3 (tty always reachable) for a host singleton: the supervisor's tty is the rk-gui window on the rk-daemon server. The tile's empty state and the palette get a GUI: Open supervisor logs action that navigates there. No relay sniffing anywhere.

2. The naming collision

"Desktop" already means three things in this repo: the Electron viewer shell (app/desktop, rk desktop install, desktop-shell.md, session rk-desktop), the wide-viewport branch in every UI memory file ("desktop vs mobile"), and — in the specs — this lens. A fourth, user-facing "Desktop" button next to a CLI whose rk desktop installs an Electron app is a trap.

Recommend the kind gui, label "GUI", CLI rk gui. In a tty-centric tool it is the honest antonym: tty vs gui. Alternatives: screen (collides with viewport/screen-size prose and GNU screen), display (collides with rk skill display). The spec rows saying desktop get updated in the same change.

3. One per host vs one per tab

Your instinct is right, but for a slightly different reason than cost. A bare Xvnc at 1080p is a few tens of MB and idle CPU; displays are cheap. What is expensive and, more importantly, stateful is what runs in them: Chrome's single-instance lock, D-Bus session, keyring, XDG dirs. PR #71 had to invent per-desktop XDG isolation plus Chrome wrapper scripts to make two desktops coexist. That is the real signal: apps assume one GUI session per user.

One per host (v1)
  • Every agent pane exports the same DISPLAY; "open a browser" from any tab lands on the one screen the human is watching.
  • Substrate = a host service, like code-server. Availability derives from a socket, no per-window option needed.
  • Multiple viewers (phone + laptop + operator) share it in VNC shared mode.
  • Cost bounded: one WM, one Chrome profile.
Per tab / per tmux session (later, if ever)
  • Needed only when two agents must run isolated GUI apps concurrently (parallel browser tests).
  • Would add a per-session display option (@rk_ses_gui) as the tile's content selector — the code content-selector shape. The tile, relay, and renderer don't change.
  • Requires the XDG/Chrome isolation machinery PR #71 wrote. Keep it in the salvage bin.

Design rule to keep the door open: the relay endpoint takes a display id (/ws/gui/{id}, v1 always host), and the state-stream payload is a list even when it has one entry.

4. What "desktop" means: Linux vs macOS

Linux (headless VM like this one)
  • We own a virtual display: no human is logged into a GUI, so rk creates one. Xvnc is an X server and the VNC server — no Xvfb + x11vnc double hop (PR #71's stack).
  • Window manager of choice: this host has kwin_x11 only; a light WM (openbox/xfwm4) is a one-line apt. Full DEs need dbus-run-session; PR #71 documented the traps.
  • X11 over Wayland for v1: every agent tool (xdotool, Playwright, import screenshots) works on X11; wlroots-headless + wayvnc is viable later but agent input injection is harder.
  • Disposable: rk gui off kills the session; state lives in $HOME like any process.
  • No GPU on GCP → software encode only; 16 cores make Tight/JPEG or x264-ultrafast trivial.
macOS (laptop or Mac mini)
  • There is exactly one GUI session: the logged-in user's. We can mirror it (Apple Screen Sharing = VNC on :5900 with ARD auth; noVNC supports security type 30) or extend it with a virtual monitor via the private CGVirtualDisplay API (PR #71's rk-virtual-display, also SimpleDisplay/BetterDisplay).
  • A true second desktop means a second user login (fast user switching over VNC) — slow, awkward, not v1.
  • Mirroring a live Mac means every VNC keystroke lands in the human's real session. Default view-only on macOS, with an explicit "take control" toggle.
  • Tahoe gotchas: Screen Sharing only accepts connections after an SSH login post-reboot; FileVault blocks auto-login; VNC caps at 1080p without a dummy plug or virtual display.
  • XQuartz + Xvfb (PR #71's macOS path) gives an X11 desktop that runs no Mac apps — not what anyone means by "the Mac's desktop". Drop it.

Consequence: the tile, relay, and client are identical on both OSes; only the backend the supervisor launches differs (Xvnc vs "dial localhost:5900"). The macOS virtual-display tool is a later, optional backend — it is the only route to "an agent's own screen on a Mac that doesn't steal yours".

  • No new env keys (Constitution IV): socket path and display number are conventions; rk gui env prints them.
  • No DB (II): availability = PATH probe; reachability = socket dial; running = session exists. Deleting the socket file degrades to "not running".
  • Survives rk restarts (VI): tmux owns the process; rk reattaches the relay.
  • Security (I): exec.CommandContext argv slices; the socket is 0600 in a 0700 dir; VNC auth is None because the only client is rk on the same user — identical to code-server's --auth none. macOS credentials: the Screen Sharing password lives in the login Keychain, read via security find-generic-password, never in config.yaml.
  • Frontend: GuiSurface is a peer of CodeSurface; @novnc/novnc RFB with scaleViewport/resizeSession; bottom-of-tile controls per current house vocabulary; focus steal-guard and chord reclaim reuse the code tile's seams.

7. Performance plan

"Really smooth" needs a definition before a stack. Proposed targets on this VM over Tailscale: click-to-pixel under 100 ms, sustained 30 fps while scrolling a browser page at 1080p, under 1 core of Xvnc CPU. Measure with a Playwright spec that scrolls a page in the guest and samples noVNC's frame counter; keep the numbers in the change's acceptance.

  • Encoding: Tight with JPEG quality 6–7 and compression 2 is the noVNC default and where Proxmox/GCP consoles live. Lossless refresh after idle is a TigerVNC server option worth turning on for text.
  • Frame rate: Xvnc FrameRate=60; noVNC requests continuously while focused, backs off when the tile is unfocused or the tab is hidden (saves phone battery).
  • Resize policy: the desktop follows the most recently focused fine-pointer viewer's tile size via SetDesktopSize (that is how one viewer stays pixel-perfect); other viewers scale client-side. Phones never drive resize — a 390 px desktop would wreck the laptop viewer's layout. A palette GUI: Lock resolution pins it.
  • HiDPI: render at CSS pixels (1×) by default; a GUI: Retina toggle doubles the framebuffer for the viewer that asked. 4× pixels is real cost on software Tight.
  • Local cursor: noVNC renders the cursor locally (Cursor pseudo-encoding), so pointer latency is client-side — this is most of what "feels smooth".
  • Upgrade lane, gated on the measurement: if the numbers miss, swap the Linux backend for KasmVNC and either iframe its proxied UI (the code-server integration shape — one afternoon) or vendor its client fork into the tile (keeps rk chrome). Selkies if audio or 60 fps video become requirements. Neither touches the tile model.

8. Mobile

  • Gestures come from noVNC: one-tap click, two-finger tap right-click, long-press drag, two-finger drag scroll, pinch to zoom when the viewport is clipped. Pan by drag when zoomed.
  • Two view modes: fit (whole desktop scaled to the tile — readable overview) and 1:1 (clip + pan — precise clicks). A single chip toggles; default fit.
  • Keyboard: the soft keyboard needs a focusable text sink; noVNC has one. The bigger win is the existing compose strip: route its text into the GUI as a paste (ClientCutText + ⌘V/^V) so phone typing into a browser field works like typing into a tmux pane today.
  • Desktop shape on a phone: don't resize the shared desktop to portrait (policy above). If a phone-first workflow shows up, a portrait second display is exactly the per-session case in § 3.
  • Bandwidth: cap JPEG quality lower on coarse pointers; noVNC exposes qualityLevel/compressionLevel per client.
  • Battery: stop framebuffer requests when the tile is hidden or the PWA is backgrounded.

9. Zen, zoom, and true fullscreen

  • Zen (⇧Enter) already hides the top bar and sidebar and zooms the focused tile. With the GUI tile focused that is "almost fullscreen" for free. Nothing to build.
  • Absolute fullscreen = element.requestFullscreen() on the tile, plus navigator.keyboard.lock() in Chromium so Esc, ⌘W, ⌘T reach the guest instead of the browser. New tile-header verb and palette entry GUI: Fullscreen; Esc held one second exits (the Chrome convention under keyboard lock).
  • iPhone cannot fullscreen a div — Safari only fullscreens video elements on iPhone (iPad and Mac are fine). The honest fallback on iPhone is zen inside the installed PWA (display: standalone already ships), which is edge-to-edge minus the status bar.
  • Chord conflicts: inside the GUI tile, ⌘K / ⌘1-4 / ⌘; are rk's; everything else goes to the guest. Same demotion class the code tile uses. Fullscreen + keyboard lock flips all chords to the guest.

10. The agent side

This is the part PR #71 didn't have and the reason to build the feature: an agent gets a computer.

  • rk gui env → DISPLAY=:N for eval; rk agent setup exports it into every managed pane so chromium, xdg-open, Playwright headed mode just work.
  • rk gui exec <cmd…> runs a command on the display (the rk code exec shape).
  • rk gui shot [--out f.png] screenshots the display — the agent can see the GUI it is driving. Pair with xdotool and you have a computer-use loop without any vendor API.
  • rk gui on|off|status (§14), and rk skill gui as the briefing page.
  • Later: a @rk_win_gui_note-style "this tab owns the GUI right now" marker so the sidebar shows which agent is driving the screen.

11. Things not yet on the list

  • Clipboard both ways: RFB cut-text (TigerVNC extended clipboard handles UTF-8); browser side needs a user gesture for navigator.clipboard.read. Palette GUI: Paste as the deterministic path.
  • Audio: not in VNC. Out of scope for v1; the route is PulseAudio null sink → Opus → WS → WebAudio (Selkies' pcmflux does exactly this).
  • Cursor fights: shared mode means two humans and an agent can all move the mouse. Inherent to one-screen; the per-session escape hatch is the answer if it hurts.
  • IME / dead keys: noVNC sends keysyms; non-Latin input via the compose-strip paste path is more reliable than live keysyms.
  • Lifecycle and cost: Chrome in the desktop eats memory forever. Never auto-kill the desktop (apps matter); show uptime + RSS in the settings row and the tile's hover state so the rk gui off decision is informed.
  • Safety on macOS: mirroring the live session means an agent-driven click could hit the human's mail client. View-only default; "take control" is a deliberate act; log every control grant.
  • Remote hosts: rk remote reaches a remote rk over an SSH tunnel; the GUI socket, supervisor, and relay all live on the remote. Nothing special, but the double hop adds latency — measure there too.
  • e2e on CI: Xvnc is apt-installable on runners; capability-gated specs skip cleanly when absent, the same as the existing plan's risk register.
  • Licensing: TigerVNC (GPL) and KasmVNC (GPL) run as external processes, fine; noVNC is MPL-2.0 as a bundled lib; Selkies MPL-2.0.
  • Wayland: Chrome and most toolkits run fine under XWayland later; keep X11 until an agent tool needs Wayland.
  • Screen recording: an agent's GUI session is worth recording (ffmpeg x11grab to a file) for post-mortems — cheap once the display exists.
  • File transfer: drag-drop into the tile → the file lands in $HOME via the existing 50 MB upload path, then the agent uses it. Not a VNC feature; an rk one.
  • Multi-monitor: no. Constitution IV.

14. Turning it on and off decided 2026-09-09: explicit user choice, never on by default

Two facts have to line up: the VNC process runs only because a human asked, and the 4th toggle button exists exactly when the GUI is enabled. One switch does both.

gui.enabled — a boolean in the settings registry, default false
  • Where it lives: ~/.config/run-kit/config.yaml behind internal/settings (Constitution IV: per-instance preference, settings-registry home; no env form — env stays the three binding keys). The registry already has bool keys (boolValue), so the settings dialog — the one permitted settings surface — grows the row automatically.
  • On: the daemon ensures the rk-gui supervisor session (Linux: Xvnc + WM; macOS: nothing to spawn — the relay dials Screen Sharing), the state stream flips gui[0].enabled, every connected tab shows the 4th button. While enabled, the daemon re-ensures the session on boot, the ensureCodeServer shape — the user opted in once; rk restarts don't un-opt them.
  • Off: the button disappears from every tab, open gui tiles degrade out of @rk_win_layout via the existing ladder (the option is left as written, so re-enabling brings them back), and the rk-gui session is killed. Killing it kills every app on the display, so off is a confirmed action: the settings toggle shows what is running ("Chromium, 3 windows · up 4h") before it proceeds; the CLI prints the same and asks unless --yes.
  • Never on by default: rk doctor shows gui: off; no install step, update, or backend probe flips it. A host with Xvnc installed still shows no button until someone turns the switch.

Two-tier alternative considered and rejected: a separate enabled preference plus a non-persisted running state (start/stop buttons). It doubles the states a user has to reason about ("on but stopped?") and the payoff — a smaller idle footprint — is a few tens of MB for an idle Xvnc + WM. If a heavy idle desktop ever matters, Xvnc -MaxDisconnectionTime is a one-flag idle policy that keeps the single switch.

15. KasmVNC, explained

What it is. A fork of TigerVNC by Kasm Technologies (GPL v2, 2020→), shipped as kasmvncserver deb/rpm/apk. It is the engine under Kasm Workspaces and LinuxServer.io's webtop images, so it is the single most-deployed "Linux desktop in a browser tab" server. Like TigerVNC's Xvnc it is one process that is both the X server and the VNC server — but it also embeds an HTTPS/WebSocket web server that serves its own browser client. No websockify, no Xvfb.

What it changed. Kasm deliberately broke from the RFB spec to optimize for browsers:

  • Encoding: WebP tiles alongside JPEG, chosen per region; multi-threaded server-side encoding; a dynamic quality loop that lowers quality while pixels move and does a lossless refresh when they stop. 1.4 (Oct 2025) added multi-threaded async decoding in the client and a big CPU cut.
  • Video streaming mode (1.5, Jul 2026): H.264 / H.265 / AV1 with VAAPI (Intel/AMD), NVENC (NVIDIA), or software encoders, decoded in the browser (WebCodecs). This is the "buttery" lane — full-frame video codec instead of tiles when content is moving.
  • Client extras over a data channel: seamless clipboard through the browser Clipboard API, file upload/download, multi-monitor (each monitor a browser window), touch input, Keyboard API for exact key handling, relative mouse mode (1.5), watermarking and other DLP knobs.
  • Server extras: DRI3 GPU acceleration for apps in the session (1.1), unix-socket relays for containerised setups (1.2), YAML config with env-var overrides (1.5), a user file with per-user permission levels (view-only / control / owner), HTTP basic auth or none, optional systemd units.

Where it would sit in run-kit. A second Linux backend behind the same gui[] payload and the same on/off switch: the supervisor launches kasmvncserver bound to a unix socket with auth and TLS off; rk reverse-proxies its HTTP + WS under a fixed route (the /code/ machinery, byte for byte); the tile renders its client in an iframe — the exact shape the code tile already has. Everything in §7 (resize follow, quality, clipboard, touch) is then Kasm's job, not ours.

Why it is attractive
  • Best perceived smoothness in the VNC family today, plus a real codec lane, with zero custom media code.
  • One binary replaces Xvnc + our noVNC renderer + the resize/clipboard/touch/quality UX in change 3.
  • Battle-tested for exactly this use (webtop).
  • Same relay boundary: unix socket, same user, proxied by rk.
Why it is not a drop-in
  • Stock noVNC cannot connect to it. Its client is a diverged fork. Either iframe Kasm's UI or vendor the fork — and the fork's ability to still talk to a standard server (the macOS Screen Sharing path) is unverified. Realistically: two renderers — Kasm iframe for Linux, noVNC canvas for macOS.
  • Linux only, so it never helps the Mac.
  • Iframe debt: chords swallowed unless focus-hopped (the code tile carries the same seams), Kasm's own control bar and side panel inside our tile (hideable via its settings — verify), its connection state invisible to our dot except via a reachability probe.
  • Its own HTTP server, TLS, auth and YAML to neutralise; version drift tracked like code-server.
  • Host packages: Ubuntu/Debian/Fedora/Alpine/openSUSE; not in Ubuntu's own archive — a GitHub release deb, so rk gui on needs an installer rung like rk code-server install.
My read. Since macOS view-only is in v1, the noVNC canvas renderer must exist anyway; KasmVNC is therefore purely additive, never a replacement. So the question is only when. Recommended: a one-day spike before change 2 — install KasmVNC 1.5 on this VM, bind it to a unix socket with auth off, proxy it through /proxy, iframe it, and judge three things: can its chrome be hidden, does its client behave on a phone, and how does scrolling a browser page feel next to Xvnc + noVNC over Tailscale. If the answer is "clearly better", change 2 builds the Kasm backend as the Linux default and Xvnc becomes the no-install fallback; if not, the plan stands as written and Kasm stays the measured upgrade lane.
